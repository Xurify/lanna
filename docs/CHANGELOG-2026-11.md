# LangHarness, November 2026: what was built, when, and what is still unverified

Times are UTC. "Unverified" means the owner has not yet used it in the live app; the sandbox checks and the tests were run in the cloud.

## 9 November: sign in with a password at a public address (branch `feat/web-sign-in`)

- **Why:** the owner wants LangHarness on the phone with the PC off, at an address of its own and with no Tailscale app ([plans/always-on-server.md](plans/always-on-server.md), route W). Rule E90.
- **What changed:** with `LH_PUBLIC_HOST` set, the app answers one public host behind a reverse proxy. Every request must carry the proxy's secret (`LH_PROXY_SECRET`), the right host and HTTPS; a page without a session goes to `/login`, the API answers 401, and a change needs the page's own Origin. One owner password (scrypt) opens a 180-day browser session that Settings → Devices lists and signs out. Wrong tries are limited per address and overall and the count is kept in the file. A changed password or a switch-off signs every device out.
- **Commands:** `npm run web:password` (set or change it; the first one turns web access on) and `npm run remote:code` (a pairing code in the terminal for a machine with no screen; `-- --enable` turns remote access on first).
- **The proxy secret is not in the plan.** The plan said to accept requests "from loopback", but Next 16 does not tell `proxy.ts` who connected, and nginx's default `Host` of `127.0.0.1:3010` would have looked like this computer. The secret replaces the peer check, and the local shortcut is off at the public address.
- **Checked in the cloud, on scratch data:** 62 new tests across the gate rules, the throttle, the password record, the store (including eight parallel guesses), `proxy.ts` itself with real `NextRequest` objects, and the login form's markup. The hidden password prompt through a pseudo-terminal (not echoed). A real Next dev server in public mode driven with curl: redirect, 401, 403 for a missing secret, the wrong Origin, plain HTTP and the nginx-default Host; sign-in, the cookie's flags (HttpOnly, SameSite=Lax, Secure, 180 days), sign-out, and the lockout with spoofed `X-Forwarded-For` entries. nginx 1.24 in front of it: its default `Host` is refused, the guide's configuration works, a client's own secret, proto and host headers are overwritten, and the throttle keys on the address nginx appended. The sign-in page in Chromium at 1280 and 390 px, Day and Night: a 16 px field, a 44 px button, no sideways scroll, no layout shift when an error appears, and a right password lands on the page that was asked for.
- **Found on the way:** the app's `text-base` is 14 px, and the shared `Input` drops to 14 px from 768 px, so the pairing page's fields (E21) still make Safari zoom on a phone and on an iPad in portrait. The sign-in field is set to 16 px by hand; the pairing page is not changed here.
- **Unverified:** a real VPS, certificate and domain; Caddy; a CDN in front; a phone or an iPad; iOS password autofill; server events through nginx under load.

## 9 November: the server as a container (branch `feat/server-container`)

- **Why:** the owner cannot always be at the PC, and the phone app only works while the PC runs. Rule E91, guide [server.md](server.md).
- **What was built:** a `Dockerfile` and `compose.yaml` for the server (the app, Chromium, a pinned yt-dlp; non-root, read-only, no capabilities, port on loopback only); `scripts/boot-check.mjs`, which starts the server on throwaway data and checks it; `scripts/update-server.sh` (build, boot-check, switch only on a pass, roll back, keep three images, push server-edited cheatsheets to a `sheets/<date>` branch); `scripts/backup-data.sh` with `scripts/verify-data.mjs` (dated snapshots, every JSON file read back, restore, copy to another machine); and `docs/server.md` for a VPS and a Synology NAS.
- **What the boot check found:** yt-dlp cannot run from `/tmp` when Docker mounts it `noexec`, which is its default for a tmpfs. The compose file and the update script now mount it with `exec`.
- **Checked:** the image builds; the boot check passes inside it (no network, read-only, user 10001); compose starts it healthy with the port on loopback only and refuses a connection through the host's other address; the container refuses to start with a clear message when a mounted folder is not writable; the update script ran update, a second update, rollback and the skip after a rollback against real Docker; backup and restore ran on real files; 22 tests in `tests/server-scripts.test.ts` (temporary git repos, a stand-in `docker`, real rsync); typecheck clean. The idle app uses about 260 MiB; the image is 1.77 GB.
- **Unverified:** everything on the owner's machines (the NAS, the VPS, a reverse proxy, YouTube from the VPS); an arm64 image; the systemd units; yt-dlp updating itself when the network allows it; `--push-to` over ssh; Chromium's memory under the tutor; moving real data. The guide lists them.
- **Needs the sign-in work:** a public address. Until then the app answers every request for a public name with 403, and the server is reached over Tailscale.

## 9 November: a security pass before the app gets a public address (branch `chore/web-security-pass`)

- **Why:** the plan for a web version ([plans/always-on-server.md](plans/always-on-server.md)) puts the app on the internet behind a sign-in. The review is [research/web-security-review.md](research/web-security-review.md); the rules are E92.
- **The tutor's page and PDF fetches** go through one guard: public addresses only, every redirect checked again, the connection made to the addresses that were checked, and the redirects, time and size capped. Before, a page the model had read could make it fetch the app's own API on `127.0.0.1`. A caption track is fetched only from YouTube's own address, and the SVG drawing fallback no longer runs script.
- **Every route that takes a body** answers 413 over a limit (256 KB for JSON, up to 8.25 MB for a recording). A test fails when a new route skips the check.
- **Keys:** the error text from a speech or voice provider is cleaned of every key before it reaches the page. A test seeds fake keys and sign-in tokens and calls every GET route.
- **Subscription sign-ins** (ChatGPT, Copilot, Grok) answer 403 while `LH_PUBLIC_HOST` is set.
- **Headers:** every response sends the usual protective headers; a production build also sends HSTS and a content security policy that blocks images, requests, sockets, frames and scripts to hosts the app does not use.
- **Checked:** 222 new tests (guard 88, body limits 69, hostile ids 52, keys 8, headers 3, subscriptions 2, plus the stubs converted in three older files); a production build in Chromium: sixteen pages load with no policy violation, and an image, fetch, socket, frame and script to another host are all blocked; the microphone and the dictation worklet still work.
- **Unverified:** YouTube's player, Deepgram's dictation and Google avatars under the policy (the sandbox cannot reach them); the SVG fallback in a real browser; the owner's PC. React's hydration warning (#418) appears now and then on Today, Review and Watch in a production build; it also appears with the policy removed on Today and Review, and on Watch only with the policy (9 of 54 loads against 0 of 37), which does not show the policy is the cause. If Watch shows it after this ships, remove the CSP header first.
- **Open:** inline script is still allowed (a nonce has to come from `proxy.ts`); a process on the same machine counts as "this computer" and passes the gate; nine dependency advisories are accepted with reasons in the review.

## 8 November: automated single-case experiment & input-first arm (branch `t3/pronunciation-principles-review`)

- **Automated SCED Protocol v3 (E82):** Single-case interrupted time-series design over 42 days (2026-11-09 to 2026-12-20) comparing Russian (input-first arm) against Slovak (normal control) to test whether input-first accelerates listening comprehension without harming speech.
- **Deterministic Randomization:** Mulberry32 PRNG with seed `20261108` drawn uniformly across candidate days [12..22] yielded **Day 15 (Monday 23 November 2026)** as onset day. Baseline runs Days 1–14 (14 days > 8 min); Intervention runs Days 15–42 (28 days > 8 min).
- **Strict Input-First Arm:** `INPUT_FIRST_TASKS = ["review", "listen", "words", "read", "watch"]` (`src/core/curriculum.ts`). Drops `lesson`, `strengthen`, `blitz`, `speak`, and `fluency` (which recorded speech via microphone).
- **Automated Execution ("Take me out of the loop"):** In `src/server/lesson.ts`, `progressSummary` automatically resolves `getScheduledArmForDate(profile, date)` and enforces the arm from Day 15 onwards without manual intervention. Synchronizes daily first-play understanding share, dictation reps, minutes, covariates, and task compliance to `daily.jsonl` on every session, continuously updating OLS regression ($b_0, b_1, b_2, b_3$), permutation test $p$-value, and `summary.md`.
- **Pre-generated Pools & Schedules:** Deterministically generates `experiment.json`, `schedule.json`, `probe-pool.json` (60 listening probes + 30 production prompts per language from verified lexicon examples), `daily.jsonl`, `checks.jsonl`, `deviations.jsonl`, and `summary.md`.

(Backward-compatible redirect from `/experiment` and `/experiments`).
  - `/experiments/input-first/check`: Sunday check session presenting 10 single-play dictation probes and 5 spoken production prompts, scored and saved to `checks.jsonl`.
  - `/api/experiments/input-first` & `/api/experiments/input-first/check`: Descriptive API endpoints with `/api/experiments/input-first/reset` to restart from Day 1 on any chosen start date.
  - **Sidebar Integration:** Integrated under the **Track** section with `FlaskConicalIcon` as "Study" (`/experiments/input-first`), accessible from any screen in the app.

## 3 November: listening trends (`feat/listening-trends`)

- **Listening trends** (E38, [research/listening-trends.md](research/listening-trends.md)): My mistakes has a Listening section. A typed sentence is compared with what was played and each difference gets a cause (a word not met, vowel length, soft or hushing consonants, voicing, a short word dropped, a word not caught, a different word heard, the wrong ending, i for y, a typing slip), shown per 100 sentences lately against before with "less often / more often / about the same". - **Checked:** unit tests, and a production build against 18 synthetic sessions over five weeks (a drop of "short words dropped" from 15 to 1 in 100 showed as "less often"). **Unverified:** a real learner's history.
